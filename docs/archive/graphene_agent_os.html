Agent OS
A system-level AI assistant on a GrapheneOS fork

Prompt the phone. Drive any app. Keep the model where you choose: on the device, on your own GPU, or, if you opt in, in the cloud.

Mohammed Husari · 5 November 2026Confidential · page 1
What we want

One assistant that can do anything you can do on the phone

1Prompt, don't tap

"Reply to Ali that I'm 10 minutes late." "Order my usual." "What did I miss on Signal and WhatsApp?" Voice or text, with a wake word that works with the screen off.

2Every app, not a chosen few

Messaging, email, maps, shopping, delivery, banking (read-only), browser: the agent reads any screen and acts in any app, with no per-app integration.

3Local-first and private

Models run on the phone or on a GPU you own. Nothing leaves the device unless you allow it, per app and per role. Cloud is an option, off by default.

Non-negotiable

  • Full control of the OS and device. Nobody else decides what the agent may see or do.
  • Safe against hostile content. A message or web page must never be able to trigger an action by itself.

Explicitly not a goal

  • Faking a different device to pass bank or app security checks.
  • Automating logins, payments or identity verification without a real touch.

The landscape

Everyone with a system-level agent is a platform owner

Gemini screen automation (Google)

Beta since Feb 2026 on Galaxy S26 and Pixel 10. Multi-step tasks in Uber, DoorDash, Grubhub. US and Korea only, selected apps, cloud model. Works because Gemini is privileged Google system software.

Doubao Phone Assistant (ByteDance + ZTE Nubia)

Dec 2025, Nubia M153, China only, ~$495, sold out. ZTE's Android granted ByteDance's agent INJECT_EVENTS. Within days WeChat, Alipay, Taobao and banks logged users out ("abnormal login environment"). WeChat control withdrawn 3 Dec.

EU DMA decision (16 July 2026)

Google must give third-party assistants equal access to 11 features Gemini uses, incl. screen automation and on-device models. Deadline Android 18 / 1 Aug 2027. Five features may need certification. Unclear if it reaches AOSP.

App-level tools

Tasker (automation + AI generator, MCP servers), gos-ai (GrapheneOS-targeted assistant), Liquid Apollo / LEAP (on-device LFM models), Omarchy mobile (Linux replacing Android). Useful parts, none has system privileges.

Takeaway: the agent is the easy part; the privileges are the hard part. Google grants them to itself, ZTE granted them to ByteDance. We grant them to ourselves by owning the OS.

Why this approach

Fork GrapheneOS: we hold the ZTE role and the ByteDance role at once

  • Full control of the OS layer. Platform signing key, system services, permissions, SELinux policy. Nobody to ask.
  • Hardening for free. GrapheneOS's memory tagging, exploit mitigations, sandboxed Google Play, per-profile encryption all come with the base. We only add the agent.
  • Pixel hardware, no hardware project. Titan M2, Tensor TPU, verified boot with our own key, relockable bootloader.
  • Local-first by construction. GrapheneOS ships no AI and no telemetry. Every model byte path is ours to define.
  • Safety enforced below the agent. Policy and confirmation live in system_server, so even our own agent (or a prompt injection driving it) cannot bypass them. Only an OS owner can build this.

Summary spec · safety

Full power, but the agent can never approve its own actions

1Trusted confirmation

Send, pay, delete, post and install route through AgentManagerService, which shows a SystemUI prompt that ignores injected input. A malicious message can steer the model; it cannot press the button.

2Planner / reader split

The planner sees labels ("3 new Signal messages from Ali") and is the only part that can call tools. The reader sees raw content and can only summarise or draft, so injected text ends up in a summary, never in an action.

3Per-app grants and an action log

One policy store, one screen, enforced in the OS. Every action is logged. Biometric prompts stay in secure hardware, so real payments still need you.

Lessons from Doubao

  • The tech worked; the ecosystem pushed back. WeChat, Alipay and banks detected the agent server-side and logged users out. A famous product on one phone model is an easy target.
  • Human-like pacing on taps and reads, so behaviour doesn't read as a script.
  • Don't automate logins, payments or identity checks. Doubao withdrew these after the backlash; we exclude them from day one.
  • Every app must still work by hand. If one objects, we stop automating it. We do not disguise the device or agent to defeat an app's security checks.
  • Shipping to others changes the picture. A personal fork is invisible; a popular agent phone gets the full Doubao treatment.

Known limits and risks

What the fork costs, and what still can't be driven

Banking apps and attestation

Behaviour checks: we pass (no accessibility service, native input). Hardware attestation: Titan M2 reports our signing key, which no bank recognises. We lose only the banks that specifically accept GrapheneOS's key; apps that check nothing keep working, apps that need Play Integrity already fail on GrapheneOS.

Bank checksGrapheneOSOur fork
Nothing (most)WorksWorks
Accepts GrapheneOS keyWorksFails
Play Integrity deviceFails (~10%)Fails

Update burden

GrapheneOS releases often. Every release means rebase, build, sign, OTA. This is an ongoing job, to be automated with a capability test suite (~20 apps) run on every build.

Still out of reach

Biometric prompts, CAPTCHAs and liveness checks, DRM video (black even to the OS), data that never reaches the phone, server-side bans for bot-like behaviour.

Model capability

Open screen-reading models (UI-TARS, Qwen-VL, AgentCPM-GUI) handle short tasks in known apps; long tasks across unfamiliar apps break. Skills library and home GPU are the mitigation.

The daily jobs, the banking / fintech apps in use (check each against the attestation table), and what the "FT app" is: Financial Times or a fintech app.
