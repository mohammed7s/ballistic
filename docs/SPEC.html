Ballistic: technical specification

Draft v0.2, 5 November 2026. Supersedes docs/archive/graphene_agent_os_spec.md (v0.1), which predates the discovery that Android 17 already ships Computer Control, AppFunctions and an empty on-device model-host socket. Context and decisions: docs/CONTEXT.md.

1. Summary

Ballistic is a build of GrapheneOS for Pixel phones, signed with our own keys, plus an assistant app. The OS-side changes are small: they turn Android 17's existing assistant machinery (Computer Control, AppFunctions, OnDeviceIntelligence, hotword) from Google-gated into user-gated, add a per-app policy service, and require hardware-backed confirmation for irreversible actions. The assistant app holds no dangerous permissions of its own; everything it does goes through those gates. Models run on the device, on a user-owned GPU, or (opt-in, off by default) in the cloud.

Design rule: the agent can touch anything on the phone except the confirmation dialog.

2. Goals and non-goals

See README.md. Short form: prompt the phone; any app; local-first; injection-safe; owner in control; built to be merged. Not: attestation spoofing, automated payments/logins/identity, hiding from fraud detection, a new OS brand, upstreaming the agent itself.

4.1 Assistant app (apps/assistant)

Ordinary APK, also buildable into the image. Holds the assistant role (user-granted). Contains the VoiceInteractionService (long-press, hotword hand-off), STT/TTS clients, planner loop, reader, skills library, routing client, overlay UI, settings UI. Permissions: assistant role, binder to the policy service, Computer Control session ownership (granted through the user gate), AppFunctions execution (through the user gate), INTERNET (subject to GrapheneOS's Network toggle). Never INJECT_EVENTS, screen capture, or accessibility-service status.

4.2 Model host (platform/modelhost)

Implements OnDeviceIntelligenceService (metadata, model management) and OnDeviceSandboxedInferenceService (isolated process doing the inference). Runtimes: llama.cpp (GGUF) and LiteRT-LM with the Tensor TPU delegate; whisper.cpp for STT; Piper for TTS. Models are downloaded, verified by hash, stored under the host's data dir. Any app the user allows may use it through the AOSP OnDeviceIntelligenceManager API; the assistant app is the first client. STT and hotword are pinned to this host and cannot be routed elsewhere.

4.3 Policy service (platform/services/assistant, in system_server)

The one place that knows the user's policy. The assistant app asks it before every observation or action; Computer Control and AppFunctions calls from the assistant app are wrapped by it.

  • Policy store: per app and per profile: observe (none / notifications / node tree / node tree
    • screenshot), act (none / navigate / full), app-data read (off / on), route (default / device-only), confirmation (default list / always / never automate).
  • Prompt assembly: builds the planner's context from labels and structured observations and the reader's context from raw content; the app cannot bypass this (it receives assembled prompts, not raw observations, for the planner role).
  • Router: chooses the backend per role under the rules in §6.
  • Confirmation broker: classifies a pending action; high-value → Protected Confirmation, low-stakes → SystemUI dialog, else proceed. Logs the decision.
  • Action log: append-only, encrypted, viewable in Settings. AIDL: observe(pkg, mode), act(Action), confirm(Summary), route(role, payload), getPolicy(), callbacks for policy change and task interruption.

5. Capabilities

5.1 Observation

Source Mechanism Notes

Screenshot ComputerControlSession.requestScreenshot (trusted virtual display) Fallback for Flutter / RN / WebView / games; downscaled before any remote send
Notifications Policy service wraps notification access Inbox, bank alerts, inline reply
App functions AppFunctionManager discovery Structured state where apps expose it
App data Off by default; per-app SELinux grant Telegram via TDLib instead; Signal via screen only

Open: what flag Computer Control sets on injected events; whether its "limited set of target apps" is code or allowlist (see docs/CONTEXT.md §6).

5.2 Action

Preference order: AppFunction call → intent / deep link → Computer Control input (taps, swipes, text via the system keyboard) → notification inline reply. Human-like timing on injected input (randomised 80–400 ms, scroll inertia). Calls and SMS through Telecom/SmsManager, confirmation-gated.

5.3 Voice

Wake word on the audio DSP via SoundTrigger (openWakeWord or custom keyword), STT whisper.cpp, TTS Piper (RHVoice / eSpeak NG fallback), all in the model host, never routed off-device. Push-to-talk via long-press and a Quick Settings tile.

5.4 Skills

A completed task is stored as ordered steps with per-step screen signatures (package, activity, key nodes). Replay checks the signature before each step and needs no model calls; on mismatch the planner resumes from that step and the skill is updated. Per app and app version; encrypted; exportable.

6. Model routing

Role Default User-changeable
Wake word, STT Device (model host) No
Reader (summarise/draft from untrusted content, no tools) Device Yes
Vision (screen → structured description) Home server → device fallback Yes
Planner (next action; only role with tools) Home server → device fallback Yes

Backends: device (model host), home server (WireGuard, OpenAI-compatible), cloud (opt-in, off). Rules, enforced in the policy service: per-app rules win ("bank and Signal: device-only"); per- connection rules (home server on pinned home Wi-Fi, optionally fast mobile data); fallback to device on unreachable/over-budget (3 s); status-bar chip shows phone / home / cloud and cannot be hidden by the app; payload minimisation (node tree over screenshot, downscale, strip bodies from device-only apps).

Resident device models (target Pixel 10 Pro): LFM2.5-8B-A1B class planner/reader (~4–5 GB), 3B vision on demand (~2.5 GB). Home server: 30–70B instruct + a grounding model (UI-TARS / Qwen-VL class).

7. Safety model

  1. Confirmation below the agent. Send, pay, delete, post, install, settings change, policy grant → Protected Confirmation (TEE-drawn, physical press, screenshots blocked). The agent can bring the dialog up; nothing it injects reaches it. Low-stakes confirmations use a SystemUI dialog flagged so injected input is dropped while it is focused (InputDispatcher rule, only if needed).
  2. Planner/reader split, enforced by prompt assembly in the policy service.
  3. Per-app grants with GrapheneOS-style defaults: messaging = observe + act, confirm sends; banking category = notifications only, device-only, never automate; others = observe + act with the default confirmation list.
  4. Least privilege for the app. No dangerous permissions; everything via gates; SELinux assistant_app domain cannot open input devices, bind SurfaceFlinger capture, or read other apps' data without a grant.
  5. Biometrics, keystore2, DRM untouched. The agent can trigger a biometric prompt and never satisfy it.
  6. Action log for every observation, action and confirmation decision.
  7. No evasion. No device/agent disguise; stop automating any app that objects.

8. Build, signing, updates

Fork GrapheneOS at a stable tag; our patch series lives on the forked repos as one commit per feature on branch ballistic-17; manifest/local_manifest.xml overlays our repos onto GrapheneOS's manifest. Keys offline; signer isolated. CI on each GrapheneOS tag: rebase, build, flash CI Pixel, run capability + injection suites, publish OTA. Target: shipped within 7 days of upstream.
