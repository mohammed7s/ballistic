# Ballistic assistant app (`apps/assistant`)

The Android shell around the Rust core (SPEC.md §4.1, PLAN step 3, docs/ANDROID_APP.md). Kotlin and
Jetpack Compose. It supplies core's four ports and shows what core returns; it holds no agent
logic (core/README.md §15, rule 1). Pass 2 puts the real Rust core behind the prompt box:
libballistic_core runs in-process through UniFFI whenever a model is configured, and the UI says
which engine takes the run.

Package and application id: `app.ballistic.assistant`. It runs as an ordinary app with no
privileged permission.

App-private files: `files/policy.json`, `files/logs/actions.jsonl`, `files/models.json`, and
SharedPreferences `secrets`, which holds only ciphertext. Backup and device transfer exclude all of them.

## What is real and what is a stub

| Part | State |
|---|---|
| Kotlin data shapes and JSON | Real. Tested against serde output of core/src/types.rs and every recorded screen in core/tests/screens. |
| Ports | Real interfaces. Synchronous, because core calls them from its own thread and blocks on each call. |
| Engine | **Real** when libballistic_core is in the APK and a model is configured: `UniffiCoreEngine` runs core's loop in-process (same loop, prompts, filter, checks and step events as the harness). Otherwise `FakeCoreEngine.demo()` replays a fixed script. The Ask and Settings tabs say which, and why ("no model configured", "libballistic_core is not in this build"). |
| Prompt box | Real UI over `PromptSession`: gate check, one run at a time, steps as they arrive (action, why, outcome), Stop, result wording per ANDROID_APP.md. |
| Command gate | Real BiometricPrompt (BIOMETRIC_STRONG). The session locks when no Ballistic activity is visible or the screen turns off. Passkey and voice are not built. |
| Confirmation window | Real: FLAG_SECURE, overlays hidden, input filter, Back denies, a hard request needs a biometric bound to a per-operation key that signs the exact request. **Untested on a device.** |
| Policy settings | Real table. Edits need the gate unlocked. A file that does not parse falls back to the defaults. |
| Action log | Real. Typed text is hidden until the owner asks to see it. |
| NotificationScreen | Real adapter. Needs notification access. Bounds are synthetic. It cannot observe another app's screen or identify the foreground activity. |
| IntentHands | `open_app` and `wait` are real. Every coordinate op, back and home returns `not_executed: needs Computer Control`. Reply, dial and alarm exist but core cannot call them yet. |
| ModelsHttp | Real client (tested against a local HTTP server). The planner endpoint is set in Settings. Each call writes one logcat line (tag `Ballistic`: role, outcome, tokens, seconds; never content or key). |
| Command gate fallback | Debug builds only: with no strong biometric available, a test PIN (`2580`) opens the command gate. Never used for operation approval. Release builds have no fallback. |
| Voice, overlay, foreground service, in-process models | Not started. |

## Build

```
scripts/build_core.sh             # libballistic_core for arm64-v8a + x86_64, host lib, Kotlin binding
./gradlew :core-api:test          # pure Kotlin, any JDK 17+; no Android SDK needed
./gradlew :app:assembleDebug      # needs an Android SDK with platform 37 (ANDROID_HOME or local.properties)
```

`build_core.sh` needs Rust stable with `rustup target add aarch64-linux-android x86_64-linux-android`,
`cargo install cargo-ndk`, and an NDK (`sdkmanager --install "ndk;27.3.13750724"`). The exact cargo
commands are in core/README.md §15. The `.so` files (`app/src/main/jniLibs/`) are build outputs
and are not committed. An APK built without them still installs and runs the fake engine, and says
so. The generated binding `core-api/.../core/ffi/ballistic_core.kt` is committed. Regenerate it
with the script whenever `core/src/ffi.rs` changes. A binding that does not match the library
fails at load, and the app falls back to the fake engine.

`:core-api:test` includes `UniffiCoreEngineTest`, which runs the real core on the JVM through the
binding with scripted ports. It needs the host library at `core/target/release/libballistic_core.so`
(or `BALLISTIC_HOST_CORE=<path>`). Without it, those tests are reported as skipped.

### Text-only model endpoint contract

`ModelsHttp` accepts textual completions for all roles. A native tool call, legacy function
call, refusal payload or tool/filter finish signal is a terminal port error, including when
text accompanies it. Native calls never become Hands actions. HTTP failures report status,
without provider error-body excerpts; unknown metadata, refusal text and tool arguments are
not included in error prose. The key store and Stop/confirmation policies are unchanged.

Each endpoint in app-private `models.json` may opt in with `"disable_native_tools": true`:

```json
{"planner":{"base_url":"http://127.0.0.1:8080/v1","model":"your-existing-model","disable_native_tools":true}}
```

The default is false, preserving the previous request fields. When true, the client adds
only `"tool_choice":"none"`, without declaring tools. The setting follows the endpoint's
existing role fallback rules; an explicitly configured reader can leave it off. No response
format is forced on reader element IDs or other textual outputs. Token budgets and all other
generation parameters remain unchanged. There is no automatic probe, fallback or retry.

Only opt in for an endpoint accepting this request shape. Acceptance and ability to prevent
the observed Gemini tool-call response have not been measured. In particular, the reviewed
Gemini `v1beta/openai` docs do not establish `none` without `tools`. See
[the transport report](../../docs/MODEL_TEXT_TRANSPORT_20261107.md) for primary sources and tests.

### Setting up an emulator for a real run (debug build)

The key never goes on a command line or into the repository. On the host that holds it:

```
umask 077
key_file=$(mktemp)
trap 'rm -f "$key_file"' EXIT
printf '%s' "$KEY_VARIABLE" > "$key_file"
adb -s emulator-5554 shell -T run-as app.ballistic.assistant tee files/models_key < "$key_file" > /dev/null
rm -f "$key_file"
```

The debug build imports `files/models_key` into SecretStore and deletes it. It does this at
process start and from Settings > Engine > Import. `files/models_import.json`, a `models.json`, is
imported the same way. Base URL and model can also be typed in Settings > Model once the gate is
unlocked. Then grant what an owner would grant:

```
adb -s emulator-5554 shell pm grant app.ballistic.assistant android.permission.POST_NOTIFICATIONS
adb -s emulator-5554 shell cmd notification allow_listener app.ballistic.assistant/app.ballistic.assistant.adapters.NotificationScreenService
```

Or open `apps/assistant` in Android Studio. The tests read the recorded screens in place from
`core/tests/screens`, so run them inside this repository.

## Decisions taken here that the design docs leave open

- **Strict JSON.** The Kotlin side rejects unknown keys for every core type. Rust does this only for
  `HandsOp` and `HostCapabilities`. Core and shell ship in one APK, so an unknown key means a
  version mismatch. Run records (`StepEvent`, `RunResult`, log lines) are parsed leniently.
- **UniFFI boundary (decided, pass 2).** The callback interface `HostPorts` passes the same JSON
  strings as the JSON-lines bridge, so serde's shapes stay the single contract and the classes in
  `Types.kt` stay the Kotlin side. Port failures cross as `HostException`
  (`Disconnected`/`Malformed`/`Host`, = core's `PortError`). Without them a thrown Kotlin
  exception would panic core. `run` returns the harness's final line,
  `{"finished":true,"report":...}` or `{"finished":true,"error":...}`, and `UniffiCoreEngine`
  turns an error into `CoreRunException`. The alternative, UniFFI records per type, would give
  two contracts to keep in step.
- **`RustCore` exposes `run()` and `stop()`, not `step()`.** Core owns sequencing. A shell that
  stepped the loop would be deciding when to act.
- **Unsupported ops return `not_executed`**, not `error`. Nothing was dispatched, and `error` makes core
  treat the effect as unknown and stop.
- **Policy file shape**: `{"version":1,"apps":{"<pkg>":{"observe","act","route","confirm"}}}`.
  The values are snake_case forms of core/README.md §9 (`tree_screenshot`, `device_only`,
  `default_list`, `never_automate`). Signal defaults to device-only. There is no banking list yet.
- **ConfirmFloor** is a second, tighten-only check in the Confirm adapter. It can raise soft to
  hard, using the SPEC §7.1 list plus core's CONFIRM_WORDS, a non-owner value source, or
  `confirm: always`. It can refuse, for `never_automate` or `act: none`. It never lowers. The
  authority belongs in core (`core/policy`, not written yet).
- **Hard approval signs the canonical request** with a per-operation key. Core does not verify
  the signature yet, because the port returns only approved/denied.
- **Normal-level permissions added beyond the brief's list.** `HIDE_OVERLAY_WINDOWS` serves SPEC §7.1 "secure against overlay".
  `SET_ALARM` is required by `ACTION_SET_ALARM`. Neither is privileged.
- **No AndroidX ViewModel.** `PromptSession` is the prompt box's view model. It is
  application-scoped, so a run survives leaving the activity and rotation.
- **API key at rest** uses a plain Keystore AES-GCM key. androidx.security-crypto is deprecated.
- **Versions**: compileSdk/targetSdk 37 (Android 17, what the gates target and the test phone
  runs). minSdk 33 so this unprivileged APK also installs on the AndroidWorld emulator.

## Next passes

Done in pass 2: core's loop takes the port traits (`run::run`), checks Stop before every
observation, model call, confirmation and dispatch, and is exported through UniFFI. The app runs it.

1. **Update and validate the bundled core.** The verified pass-2 APK predates the Core4
   reader/readback work; its `read` and `answer` paths end as `unsupported`. Rebuild after core
   integration and test the notification reader before claiming "what did I miss?" support.
2. **Policy into core.** `ConfirmFloor` (shell) moves into core's policy, where the authority
   belongs. Core then also checks the hard-approval signature.
3. **Device checks of the confirmation window.** Measure the device id and flags of adb
   `input tap` and of accessibility clicks on Android 17. Run SPEC §9's 1,000 injected taps.
   Decide whether window-side filtering suffices (CONTEXT open question 7).
4. **Core contracts for notification reply, dial and alarm**, so core can ask for them (with
   exact-operation approval) rather than only shell code.
5. **Run lifecycle.** A foreground service while a run is active, and an "interrupted" record
   after process death (never resume mutation).
6. **Computer Control adapters once the gate lands (PLAN step 5).** These are
   `ComputerControlScreen` (accessibility proxy tree) and `ComputerControlHands` (taps, swipes,
   `commitText`, back/home). The app then builds as a priv-app with the assistant role.
7. **Voice and overlay.** Wake word, push-to-talk, STT/TTS (SPEC §5.3), then in-process models
   (LiteRT-LM, llama.cpp) behind `Models`.
